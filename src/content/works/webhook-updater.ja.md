## 概要

GitHubのWebhookを受信し、サーバー上のファイルを自動更新するPython製のサービスです。Gitリポジトリの更新と、GitHub Releaseの成果物をダウンロードして展開する方式に対応しています。

このポートフォリオサイトでも、GitHub側の更新をVPSへ反映する仕組みとして利用しています。GitHub Actionsでのビルドと組み合わせ、成果物の作成から公開サーバーへの配置までを自動化しています。

## 主な機能

- FastAPIによるWebhookの受信
- HMAC-SHA256によるWebhook署名の検証
- 更新対象のリポジトリ名、イベント種別、アクションによる条件判定
- `git pull --ff-only`によるリポジトリの更新
- 指定したリリース成果物のダウンロードとtar.gzの展開
- YAMLによる複数の更新対象と配置先の管理
- Webhookを起点としたサービス自身の更新と再起動

## 採用する利点と設計上の工夫

### GitHub側にサーバー接続用のSSH秘密鍵を置かずにデプロイする

GitHubからはWebhookで更新を通知し、サーバー自身がGitHubから必要なファイルを取得します。このため、GitHub ActionsのSecretsなどに公開サーバーへログインするためのSSH秘密鍵を登録する必要がありません。CI側にサーバーへのログイン権限を渡さずに、自動デプロイを構成できる点が利点です。

Webhookの署名検証には共有シークレットを使用します。また、非公開リポジトリなどの取得に必要な認証情報はサーバー側で管理します。

### デプロイ設定をサーバー側に集約する

更新対象ごとのリポジトリ、イベント条件、取得する成果物、更新方式、配置先をサーバー側のYAMLにまとめて管理します。たとえば配置先のディレクトリだけを変更する場合は、GitHub Actionsのワークフローを編集せず、サーバー側の設定で対応できます。

複数の制作物を同じサービスで管理でき、Gitで直接更新するファイルと、ビルド済みのリリース成果物を展開するものを、対象ごとに使い分けられます。

### ビルドと配信の役割を分ける

このサイトでは、ビルドはGitHub Actionsで行い、公開サーバーはWebhookを受けて必要な成果物を取得・展開します。公開サーバーにサイトのビルド用のNode.jsや依存パッケージを用意せずに済み、サーバー側で管理する依存関係とビルド時の処理負荷を抑えられます。

既存のVPSを使いながら、成果物を手作業で配置する負担を減らす構成です。

### 受信した通知を確認する

Webhookの署名を共有シークレットで検証し、設定したイベント条件とリポジトリ名を確認してから更新処理を実行します。署名の比較には`hmac.compare_digest`を使用しています。

### 自分自身の更新にも対応する

サービス自身への更新通知では、Gitの更新に成功した後に応答を返し、サーバーを終了します。監督プロセスが`uv sync --locked`で依存関係を同期し、更新されたサーバーを起動します。

Gitの更新に失敗した場合はサーバーを動かしたままエラーを返します。依存関係の同期に失敗した場合は停止してログへ記録し、修正または切り戻し後に再起動する運用です。再起動中は短時間のサービス中断が発生します。

## 技術構成と運用

- Python / FastAPI / Uvicorn
- Requests / PyYAML / JSON Schema
- GitHub Webhooks / GitHub Releases
- uv / Linux / systemd

`uv run main.py`で起動し、Linuxではsystemdによるサービス運用を想定しています。
